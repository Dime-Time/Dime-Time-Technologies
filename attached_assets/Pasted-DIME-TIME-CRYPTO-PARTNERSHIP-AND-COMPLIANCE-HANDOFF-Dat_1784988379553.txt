PERMANENTLY REJECTED ARCHITECTURE
==================================================

The previous proposal to route all customer purchases through one
company-controlled Coinbase account has been permanently rejected.

Dime Time will NOT:

- Pool customer crypto purchases in a company Coinbase account
- Hold customer fiat designated for crypto
- Hold or custody customer cryptocurrency
- Buy crypto in Dime Time's name for customer benefit
- Request users to create and paste manual exchange API keys
- Store API credentials capable of moving customer money
- Send customer crypto to a Dime Time-controlled wallet

That architecture could make Dime Time a custodian or money transmitter
and creates unacceptable licensing, security, accounting, and operational
risk for an early-stage solo founder.

The existing Coinbase Advanced Trade API key remains enabled, but it only
controls the founder/company Coinbase portfolio. It must NOT be used for
customer purchases.

==================================================
TARGET ARCHITECTURES
==================================================

STRATEGY A — COINBASE OAUTH BRIDGE

Each user connects their own verified Coinbase account through OAuth.

- User explicitly authorizes access
- Purchases happen inside the user's Coinbase account
- Assets remain in the user's Coinbase account
- Dime Time never holds crypto
- Users must already have or create a verified Coinbase account
- Dime Time securely stores encrypted OAuth tokens only
- Coinbase handles the customer exchange account and custody

Potential drawback:

Every participating user must complete Coinbase registration and KYC,
which may create significant drop-off among debt-payoff users who are new
to cryptocurrency.

STRATEGY B — EMBEDDED CRYPTO BROKERAGE

A licensed partner creates and maintains individually owned customer
accounts directly inside the Dime Time experience.

The partner would ideally handle:

- Customer KYC and identity verification
- Sanctions and compliance screening
- Fiat account funding
- Trade execution
- Crypto custody
- Statements and confirmations
- Transaction monitoring
- Tax reporting
- Regulatory licensing

Potential partners contacted today:

- Alpaca Broker API
- Zero Hash

This is likely the better long-term “Acorns-style” customer experience
because users would not need an existing Coinbase account.

==================================================
RECOMMENDED PRODUCT DESIGN
==================================================

Do not execute a separate crypto trade for every individual card purchase.

Recommended flow:

1. Track each eligible round-up in Dime Time's ledger.
2. Apply the user's selected debt-versus-crypto allocation.
3. Send the debt portion through the existing compliant debt-payment path.
4. Accumulate the crypto portion as pending bookkeeping.
5. Trigger a crypto purchase only after reaching a minimum threshold.
6. Have the licensed partner fund, execute, and custody the purchase.
7. Record the partner transaction ID and final execution details.
8. Show the completed purchase in Dime Time.

Potential purchase rules:

- $5 minimum accumulated crypto allocation
- Weekly purchase schedule
- User-selected monthly maximum
- Carry forward balances below the minimum
- No purchase when fees exceed an acceptable percentage
- Pause purchases after failed funding attempts
- Pause crypto without disabling debt payments

==================================================
REGULATORY AND UX GUARDRAILS
==================================================

Crypto should remain optional and off by default.

Users should explicitly select:

- Whether to participate
- Their crypto percentage
- Supported cryptocurrency
- Minimum purchase threshold
- Maximum weekly or monthly amount

Recommended initial assets:

- Bitcoin
- Ethereum

Dime Time should avoid:

- Selecting investments for users
- Dynamically changing allocations
- Rebalancing portfolios without clear user instructions
- Promising investment performance
- Suggesting crypto is a dependable debt-payoff method
- Presenting simulated balances as real assets
- Combining debt and crypto authorizations into unclear disclosures

Debt payoff should remain the primary product.

Potential conservative design:

- Debt always receives the majority of round-ups
- Crypto is off by default
- Crypto allocation is capped
- Failed debt payments may pause crypto purchases
- Users can disable crypto without disabling debt payments
- Clear disclosure that crypto can lose value
- Clear disclosure that crypto is not FDIC or SIPC protected

The final architecture must also address:

- Regulation E authorization for variable electronic transfers
- Separate debt and crypto mandates where appropriate
- User cancellation and revocation
- Error-resolution procedures
- ACH returns and insufficient funds
- Tax basis and Form 1099-DA reporting
- Data retention
- Encrypted token storage
- Account takeover protection
- Provider webhook verification
- Idempotency and duplicate-purchase protection
- Reconciliation between funding, orders, execution, and custody
