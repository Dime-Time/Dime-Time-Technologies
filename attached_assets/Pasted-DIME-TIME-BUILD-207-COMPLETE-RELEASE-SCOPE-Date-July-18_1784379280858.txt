PRIORITY 1 — PLAID OAUTH SUPPORT
MUST BE COMPLETED BEFORE BUILD 207 SUBMISSION
================================================================

PROBLEM

Plaid Production bank linking works, but OAuth institutions such as Chase may
send users to the bank’s website or mobile app for authentication.

The current iOS app cannot reliably complete the return from the bank back into
Plaid Link. This will be one of the biggest gaps encountered by real users.

IMPORTANT PLAID REQUIREMENTS

Plaid OAuth on iOS must use an HTTPS Universal Link.

Do not use a custom URI scheme as the Plaid redirect URI.

The implementation should include all of the following:

A. PLAID DASHBOARD CONFIGURATION

- Create and register an allowed HTTPS redirect URI.
- Use a controlled dime-time.com URL, for example:

  https://dime-time.com/plaid/oauth

- Confirm the exact production URI is registered in the Plaid Dashboard.
- Do not include query parameters in the registered redirect URI.
- Confirm OAuth access/approval status in the Plaid Dashboard.

B. SERVER-SIDE LINK TOKEN CREATION

Update every applicable Plaid /link/token/create call to include the exact
production redirect_uri.

This includes:

- Normal initial bank linking
- Update mode
- Account-repair/re-authentication flows
- Any other endpoint that creates a Link token for iOS or webview use

The redirect_uri must exactly match the URI registered with Plaid.

Continue using a unique, internal user identifier for:

- user.client_user_id

Do not place email addresses, secrets, access tokens, or sensitive personal
information in redirect URLs.

C. APPLE APP SITE ASSOCIATION FILE

Host a valid static Apple association file at:

https://dime-time.com/.well-known/apple-app-site-association

Requirements:

- Must be served through HTTPS
- Must not redirect
- Must be valid JSON
- Must not include a .json filename extension
- Must include the correct Apple Team/Application Identifier Prefix
- Must include bundle identifier com.dimetime.mobile
- Must authorize the exact Plaid OAuth return path
- Must be served with an appropriate JSON content type

D. IOS ASSOCIATED DOMAINS

Add the Associated Domains entitlement to the native iOS project.

The entitlement should include:

applinks:dime-time.com

Confirm the entitlement is present in the signed/archive build, not merely in
an unused local configuration file.

E. UNIVERSAL LINK RETURN HANDLING

Implement native iOS/Capacitor handling for the Universal Link that returns from
the financial institution.

The app must:

- Detect the Plaid OAuth return URL
- Preserve or recover the correct Plaid Link session
- Resume the same Link flow
- Pass Plaid the complete received redirect URI, including the OAuth state
- Avoid adding, removing, or modifying Plaid’s returned state parameters
- Prevent the redirect from opening an unrelated app screen
- Handle cold-start and already-running-app scenarios
- Handle users returning from the bank’s website or native banking app

If the current implementation uses Plaid Link through a webview, ensure that
Link is correctly reinitialized after OAuth using:

- The same Link token used before the redirect
- The full received redirect URI

Do not generate an unrelated new Link session when resuming OAuth.

F. OAUTH ERROR HANDLING

Add clear handling for:

- User cancels at the bank
- User cancels in Plaid Link
- Redirect URI mismatch
- Missing or expired Link token
- OAuth state mismatch
- Bank authentication failure
- App opened without a resumable session
- Network interruption
- User returns to the app twice
- Duplicate callbacks

Do not show a blank screen, endless spinner, or generic crash.

Provide a safe retry option that does not create duplicate Plaid Items.

G. OAUTH TESTING

Test on a physical iPhone, not only the iOS simulator.

Required scenarios:

- A normal non-OAuth institution
- Chase or another production OAuth institution
- Plaid Sandbox OAuth institution where applicable
- Bank website authentication
- Bank app-to-app authentication where available
- Dime Time closed before the callback
- Dime Time already running before the callback
- User cancels before authenticating
- User cancels after leaving Dime Time
- Invalid or expired Link session
- Duplicate return callback
- Successful public_token exchange
- Correct Item/account storage
- No duplicate connected institution after resume

Do not consider OAuth complete merely because the app opens again.

Success means:

- The user returns to Dime Time
- The original Plaid Link session resumes
- Plaid reports success
- The public token is exchanged once
- The connected accounts appear correctly
- No duplicate Item is created

PRIORITY 2 — PLAID LIABILITIES FEATURE GATING
SERVER-SIDE FIX — DEPLOY WITHOUT WAITING FOR APPLE
================================================================

CURRENT STATE

Plaid Production currently has:

- Transactions: enabled
- Auth: enabled
- Identity: enabled
- Liabilities: NOT enabled

The automatic debt-import button will error until Plaid grants Liabilities.

REQUIRED ACTION

Do not leave a known broken debt-import button exposed in production.

Implement a server-controlled capability or feature flag such as:

ENABLE_PLAID_LIABILITIES=false

While false:

- Do not call the Plaid Liabilities API
- Disable or hide the automatic debt-import action
- Do not show a generic server error
- Show a user-friendly message such as:

  “Automatic debt import is coming soon. You can add your debts manually now.”

The server should return a specific capability/error state such as:

PLAID_LIABILITIES_NOT_ENABLED

The frontend should recognize that state and present the friendly message.

When Plaid approves Liabilities:

- Enable the feature server-side
- Verify production API access
- Test with an allowlisted/internal account
- Turn on the capability
- Do not require another App Store release unless the current frontend lacks the
  required debt-import interface

The server must remain the source of truth. Do not rely only on a hidden or
disabled frontend button.

PRIORITY 4 — ROUND-UP FUNDING-ACCOUNT SELECTION
MUST-HAVE BEFORE EXPANDING REAL-MONEY ACCESS
================================================================

GOAL

Users with multiple connected bank accounts must be able to identify which
eligible checking account will fund round-up ACH payments.

FRONTEND REQUIREMENTS

- Display eligible connected funding accounts.
- Show institution name.
- Show account name/type.
- Show only masked identifying digits, such as the last four digits.
- Clearly mark the currently selected funding account.
- Allow the user to change the selected account deliberately.
- Require confirmation when changing the funding source if appropriate.
- Preserve the selection across sessions.
- Show a clear empty state if no eligible account exists.
- Explain when an account cannot be used for ACH funding.
- Never display full account or routing numbers.

SERVER REQUIREMENTS

The server must store the selected funding-account identifier.

The server must verify that:

- The user is authenticated
- The Plaid Item belongs to that user
- The selected account belongs to that Plaid Item
- The account is eligible for ACH debit
- The stored Stripe PaymentMethod or bank-payment reference belongs to that user
- The selection is active and not disconnected
- A client cannot submit another user’s account identifier
- A stale or removed account cannot be charged

Do not trust an account ID supplied by the frontend without server-side
ownership and eligibility validation.

REAL-MONEY SAFETY REQUIREMENTS

Do not weaken or remove:

- ENABLE_REAL_TRANSFERS
- Per-user allowlisting
- $1 first-transfer limit
- $5 daily cap
- Idempotency protection
- Mandate/authorization evidence
- Webhook verification
- Transfer ledger safeguards
- Duplicate-charge protections

Changing a funding account must not automatically initiate a payment.

PRIORITY 5 — ACH STATUS AND USER-TRUST CLARITY
STRONGLY RECOMMENDED
================================================================

ACH transfers are asynchronous. The interface must not imply that an ACH payment
has settled merely because Stripe accepted the request.

Use clear statuses such as:

- Pending
- Processing
- Settled
- Failed
- Canceled
- Returned

REQUIREMENTS

- Map Stripe webhook events to Dime Time’s internal transfer statuses.
- Keep the database/server as the authoritative status source.
- Explain that ACH payments can take multiple business days.
- Show the amount, destination debt, funding account, initiation date, and status.
- Clearly distinguish “submitted” from “settled.”
- Do not credit a debt as fully paid from a merely pending ACH transaction unless
  the interface explicitly labels the credit as pending.
- Provide human-readable explanations for failures and returns.
- Provide safe retry instructions.
- Ensure retries use idempotency and cannot create duplicate debits.
- Show a support path for failures that the user cannot correct.

TEST:

- Payment initiated
- Payment processing
- Payment settled
- Payment failed
- Payment canceled
- ACH returned after appearing successful
- Duplicate webhook delivery
- Webhooks delivered out of order
- User refreshes or closes the app during processing
