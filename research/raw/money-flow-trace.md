1. **Round-up collection**: `server/services/stripeService.ts:294` uses `stripe.paymentIntents.create` with `payment_method_types: ["us_bank_account"]`. Stripe is the ACH originator of record (acting as the processor). The statement descriptor suffix is configured at `server/services/stripeService.ts:311` as `(args.descriptor || "DIME TIME").slice(0, 22)`.
2. **Funds settlement**: Funds settle first in the Stripe balance. The code does not explicitly handle payouts; it relies on Stripe's auto-payout configuration (likely configured in the Stripe Dashboard to a Mercury account). No `fa_` destination logic was found in the source code.
3. **Mercury account**: Funds settle into the account matching `MERCURY_ACCOUNT_NUMBER` (`server/services/mercuryService.ts:101`). Per code comments (`server/services/mercuryService.ts:94`), this is the **Savings** account ("business_savings" in `server/storage.ts:3006`) to earn interest until disbursement. No code exists for moving funds between Mercury accounts.
4. **Creditor payments**: `server/services/weeklyDisbursementService.ts:186` (`runWeeklyDisbursement`) initiates payments via `mercuryService.initiateTransfer`. The funding account is resolved in `server/services/mercuryService.ts:98` by matching `MERCURY_ACCOUNT_NUMBER`. Payments are funded from the accumulated round-up balance sitting in that Mercury account.
5. **Transfers ledger**: The `transfers` table (`shared/schema.ts`) tracks processor events (`created`, `pending`, `settled`, `failed`). It serves as an accounting record. Per-user balance is tracked by summing settled collections and subtracting non-void payments (`server/services/weeklyDisbursementService.ts:90`). It is not automatically reconciled against bank balances in code.
6. **Commingling**: Subscription revenue (Stripe Billing) is handled via `server/services/subscriptionService.ts` and `server/routes/stripeRoutes.ts:1010`. Both subscriptions and round-ups use the same Stripe integration/account, and thus settle into the same Stripe balance/Mercury payout account. No segregation logic exists in the code.
7. **Holding period**: Funds are held until the Friday boundary (`server/services/weeklyDisbursementService.ts:67`). Funds for skipped users (e.g., balance < $1.00) roll over indefinitely as they remain "settled" in the ledger and are included in the next balance calculation (`server/services/weeklyDisbursementService.ts:102`).

### Money Flow Narrative
1. **User Checking Account**: User's bank account is debited via Stripe ACH PaymentIntent (`server/services/stripeService.ts:294`) when round-ups are collected.
2. **Stripe Balance**: Funds settle in the company's Stripe account balance after the standard ACH settlement period (typically 3-5 days).
3. **Mercury Savings**: Stripe auto-payouts transfer settled funds to the configured Mercury business savings account (mapped to `MERCURY_ACCOUNT_NUMBER`).
4. **Mercury Savings (Holding)**: Funds sit in the Mercury savings account earning interest (`server/storage.ts:3007`) until the weekly disbursement run.
5. **Creditor (Debt Payee)**: Every Friday at 00:00 ET, `WeeklyDisbursementService` calculates the disbursable balance for each user and initiates a Mercury ACH transfer (`server/services/mercuryService.ts:169`) from the savings account directly to the user's creditor (target debt).
